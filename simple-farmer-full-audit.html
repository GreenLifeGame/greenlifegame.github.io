Executive Summary

Simple Farmer is the second game on the GreenLifeGame (GLG) platform — a fruits-and-vegetables farming P2E game, deliberately built as the simple/easy counterpart to GREEN LIFE's depth. It runs on its own dedicated file set (farmer-*.jsx), its own entry point (farmer-main.jsx → farmer.html), and shares essentially nothing at the code level with GREEN LIFE — see Chapter 02 for the precise boundary of what actually is shared.

As of this audit, Simple Farmer is CLIENT SIMULATION for almost every system — no wallet, no chain, no on-chain program of any kind exists for this game yet. The one confirmed exception is its referral system, which runs against a real, deployed Supabase backend — its own schema inside the same shared multi-game Supabase project GREEN LIFE and Mother Lode also use (own database functions, own edge functions — see Chapter 12), migrated there 2026-08-28 from an earlier fully-standalone project with zero data loss — verified end-to-end with a real click-driven mint in the 2026-08-24 audit session, before the migration. The game is also live-deployed as four static subdomains under greenlifegame.com (see Chapter 16).

The four games split into two tiers, and the decay rate is paired to the pool size deliberately: Simple Farmer and Mother Lode run 0.05%/day on 200B, GREEN LIFE and Dino Island run 0.069%/day on 250B — roughly 100M $GREEN/day emitted by each of the lighter games against roughly 172.5M/day by each of the heavier ones, a 1 : 1.73 earning-power ratio. Cody's stated reason: "green life and dino island will earn more i know that, and i did it on purpose as it takes more time to play that game." Raising crop power across the board does not raise real player earnings, because the share-of-network-power math cancels it out — only pool size and rate actually move real earnings.

Scope caveat: the figures above for GREEN LIFE, Dino Island and Mother Lode come from the locked platform tokenomics, not from those games' code — no GREEN LIFE, Dino Island or Mother Lode source file was read to produce this document. Separately verified this session, directly from Cody: the lottery dataset is the only thing genuinely shared cross-game today; every other system (referrals, farm economy, inventory) is fully separate — matching the standing platform rule that every GLG game gets its own code, files, and GitHub repo, no exceptions even where mechanics overlap.

Garden Tiers & the Multiplier Mechanic

Locked rule — a garden tier multiplies power up AND divides cycle time down by the SAME number "if a veggie is 7days 1x on 2x it should be 3.5days and earn the same amount it would from 7 days but in 3.5 days." — Cody. A single harvest pays the exact same total at any tier (rate × time cancels); the only real benefit of a higher tier is throughput — more harvests per unit of real time, never a bigger single payout. farmer-constants.js:231-244; farmer-screen-garden.jsx:225-291

Worked example (both docs agree, math independently checked): a Potato at 1X is 10 days / 100 power; the same card at 5X is 2 days / 500 power — identical total payout, five times the harvests per week.

Plot purchase mechanics

  • Every plot the tier could ever reach at Lv5 is rendered up front, not just what's currently unlocked — locked cells show what unlocks them and at what price. farmer-screen-garden.jsx:86-89, 433-444
  • Plots must be bought strictly in order — only the single lowest unbought cell is tappable; every other cell reads "take plot N first." farmer-screen-garden.jsx:406-420
  • Purchases route through a real pay-with picker + wallet-sign screen (payWithSol) — fixed 2026-08-24, it used to charge SOL directly with no confirmation.

Planting — staged batch, one signature LOCKED

"when planting cards in the game make sure there is a sign to complete the task at the end... that is a final decision. weed game has this but simple farmer needs it." — Cody, 2026-08-24

Tapping a card into a plot stages it as PENDING — nothing is planted or earning yet. Pulling it back out is free, no signature. A "🔐 Confirm & Sign" bar shows the total staged count across every garden tier at once and commits the whole batch in one signature. Defensive re-checks run again at commit time (belt-and-suspenders): a staged card that vanished (sold/bred away) while pending is silently dropped rather than crashing. farmer-game.jsx:1079-1138; farmer-screen-garden.jsx:150-468

Boosting a growing plant

One active boost per plant, no stacking, no cancelling, no swapping. Duration = that plant's own full cycle, not a fixed day count (since garden tier changes cycle length up to 100×). Cannot be applied to a plant already at 100% — the game blocks it, since a boost would burn the card for nothing at that point. farmer-game.jsx:1235-1246; farmer-screen-garden.jsx:806-837

No watering mechanic exists anywhere in this game Confirmed by a full read of farmer-screen-garden.jsx — no water action, no hydration state, no "Water All" button, no reference to watering at all. Crops grow purely on elapsed time via growFrac/plantedAt+cycleMs. This is a genuine, deliberate mechanical difference from GREEN LIFE's Fast Autos, which do dehydrate and require watering.

In-tier weighting — a mechanic that doesn't exist in GREEN LIFE
"you do the odds for in class pick based on the cards value." — Cody
Once a tier is rolled, each card's weight inside it = 1/power, normalized to 100% — half the power, twice as likely. Fruit and veggie share one pool per tier, not two separate draws. Crossbreeding

Three hard rules, enforced in the picker UI AND in the handler

  1. Same-category only — Veggie×Veggie or Fruit×Fruit, never across. New behavior vs. GREEN LIFE (which allows any×any).
  2. A card at or above the parent ceiling can never be a PARENT — BREED_PARENT_MAX_RARITY = "Epic", so only Legendary is blocked as a parent, but Legendary can still come out of a breed.
    "breeding can make a legendary just can't use them to breed its pointless." — Cody
  3. No self-pairing — the same physical card can't fill both slots; duplicate copies of the same crop can pair with each other.

A real gap this closed: listings could never actually sell

Marketplace Mogul needed a genuine "you sold something" event, and none existed — a listing only ever expired (7-day TTL, auto-return) or sat there; nothing in the game ever simulated a buyer taking it. listingSellTickPct(tickMs) gives every open listing an independent per-tick chance of selling, calibrated to a constant-hazard-rate model so a listing has roughly a 65% chance (LISTING_SELL_TARGET_PCT = 0.65) of selling within its full TTL window rather than never selling or resolving instantly: 1 − (1 − TARGET)^(tickMs / LISTING_TTL_MS). Runs on the existing 1-second game clock, now read through a new shared constant, CLOCK_TICK_MS, rather than the sale-roll and the clock's own setInterval each hardcoding 1000 independently — closing a latent "if the clock tick is ever sped up for testing, the sale-roll silently mis-calibrates" risk caught in review before shipping. A sold listing pays the seller their net (after the standard fee), credits the fee to the treasury, and adds the net amount to lifetimeMarketSol — the figure Marketplace Mogul ranks on.

farmer-constants.js's own SIM_FLAGS entry for market selling was stale before this fix The pre-existing "sim-market-sell" disclosure line claimed listings could never actually sell — true before this session, false as of the sale-tick mechanism above. Corrected in the same commit as the fix itself, plus two new SIM_FLAGS entries added for the new simulated systems this chapter covers: sim-rankings-rivals (the 9-of-N fabricated rows on every board) and ranking-events-no-backend (event windows are real client logic with no server persistence).

Event windows — per-category, admin-controlled, multi-select

RANKING_EVENTS holds one {active, startedAt, name} slot per category — not one shared "current event" slot for the whole board set — which is precisely what makes running Rarest Collection and Marketplace Mogul as two independently-named, independently-timed events at once possible. A new admin panel, RankingsEventsPanel (Admin → 🏆 Rankings tab, farmer-admin-rankings.jsx), presents all 6 categories as a checklist with one shared optional event name; one sign-and-apply action starts or resets every checked category together under the same startedAt timestamp. A "Live now" list below it shows every currently-running event with an individual "⏹ End" button per category.

Each player's own event-window score is computed entirely client-side: the first moment a player's client notices a category's startedAt has changed, it captures a baseline (eventBaselines state) equal to that category's current lifetime value. From then on, the event score is current lifetime value − baseline, so a brand-new player and a 3-month veteran both start any event at exactly zero regardless of their lifetime totals — lifetime boards themselves are never touched by an event starting, resetting, or ending. The watcher effect that captures baselines uses the functional setState form specifically so it doesn't need eventBaselines itself in its dependency array (which would otherwise cause it to re-run on its own writes).

The World screen shows a 🔥 EVENT LIVE panel above a category's regular lifetime board whenever that category has a live, baseline-matched event running, using fmtDurShort for the "started N ago" line.

Bug caught before shipping — fmtDur(0) returns the string "ready," not "0s" An early draft used the game's existing fmtDur helper for the event-live banner's elapsed-time line, which is designed for countdowns and has an explicit ms <= 0 → "ready" branch. A just-started event read as "Started ready ago" — caught live while testing, fixed by switching to fmtDurShort (already correctly used for this exact purpose in the admin panel), which has no such special case.

Anything that automatically pays out the top of a board on event-end would be a separate, not-yet-scoped feature; flagged here so a future reader doesn't assume one exists because the rest of the event-window machinery does.
